01Resumen

Qué es la mesa de soporte, cómo está construida y dónde vive cada parte.

La mesa de soporte de Inncentives es un help desk inspirado en Zammad para los clientes de Inncentives. Tiene dos áreas que se distinguen por el host: el Portal de clientes y el área de agentes; cada host tiene su propia cookie de sesión y las rutas de administración solo responden en el host de agentes.

ÁreaHost en producciónNotas
Portal de clientessupportinncentives.neitek.netTambién publica /hooks/* (proveedores) y /widget.js.
Agentesagents-supportinncentives.neitek.netRutas de administración y tokens de API solo aquí.
Nombres de dominio en la documentación

La guía de despliegue y algunas integraciones todavía usan los nombres soporte.inncentives.com y agentes.soporte.inncentives.com. Producción usa los hosts de neitek.net de la tabla, configurados en public_hosts de Terraform.

02Topología y red

Cómo llega una petición desde el navegador hasta el contenedor que la atiende.

Borde: Cloudflare

  • DNS. La zona neitek.net sigue en DigitalOcean (registrar Namecheap). Los dos hosts públicos son CNAME hacia Cloudflare for SaaS, configurado sobre el dominio técnico neiteksupport.com con origen de respaldo origen.neiteksupport.com. Los registros TXT de validación también viven en DigitalOcean.
  • Túnel mesa-prod: entrega ambos hosts a http://web:8080. TLS termina en Cloudflare; dentro del túnel el tráfico llega en HTTP a nginx.
  • IP del cliente. La API solo confía en CF-Connecting-IP cuando la petición viene de nginx (172.30.15.10).
  • Controles previstos (guía de despliegue §8): reglas administradas del WAF, Bot Fight Mode en el portal, regla Skip para /hooks/, límite de 20 peticiones por minuto a /api/v1/auth/*, Always HTTPS, TLS mínimo 1.2 y HSTS, y Cloudflare Access para el host de agentes (grupos de Entra con MFA, Bypass en /hooks/*).

Red en OCI

ElementoConfiguración
VCN10.40.0.0/16; subred privada 10.40.1.0/24 sin IP pública ni entrada desde internet.
SalidaNAT Gateway para internet; Service Gateway para los servicios de Oracle (Object Storage, Vault).
Security listSe reemplaza la predeterminada por mesa-prod-default-deny. Su única regla es la salida TCP 22 hacia la subred, necesaria para que el endpoint de Bastion alcance la VM.

Acceso de operadores

Se entra con una sesión de port forwarding de Bastion hacia el puerto 22 de la VM (por ejemplo ssh -N -L 2222:<ip>:22 <sesión>@host.bastion.mx-queretaro-1.oci.oraclecloud.com) y luego ssh -p 2222 ubuntu@localhost. Las llaves públicas autorizadas se instalan desde admin_ssh_public_keys de Terraform.

Endurecimiento común

  • Sistema de archivos de solo lectura, no-new-privileges, cap_drop: ALL, usuarios no root y límites de memoria y procesos.
  • Logs JSON rotados (20 MB × 5).
  • Secretos como archivos: el tmpfs del host /run/mesa/secrets se monta en cada contenedor como /run/secrets. En producción la aplicación rechaza secretos por variable de entorno.
  • Imágenes propias fijadas por digest en /opt/mesa/images.env; las de terceros (cloudflared, redis, clamav) por tag.

04La aplicación

Cómo está organizada la API y qué mecanismos protegen cada petición.

Arranque

Fastify con límite de cuerpo de 1 MB, trustProxy y helmet. Prefijo global /api/v1, salvo /health, /ready y los webhooks de proveedores (/hooks/cti, /hooks/azure-devops, /hooks/twilio/*, /hooks/whatsapp). Respuestas con Cache-Control: no-store. La especificación OpenAPI está en /api/v1/openapi.json (requiere sesión de agente).

Módulos de la API

  • auth: login, MFA TOTP, WebAuthn, SSO OIDC.
  • policy: guardia global de autorización.
  • security: contraseñas, sesiones, tokens, cifrado de campos, rate limit.
  • tickets: tickets, artículos, macros, numeración.
  • attachments y storage: adjuntos en OCI u S3.
  • automation, rules, sla: triggers, SLA, Core Workflows.
  • overviews y search: vistas y búsqueda.
  • channels: correo, teléfono, WhatsApp/SMS, Twilio.
  • chat: chat en vivo.
  • kb: base de conocimiento bilingüe.
  • notifications y mail: avisos in-app y correo.
  • realtime y events: Socket.IO y bus de eventos.
  • reports: métricas y exportación.
  • integrations: Inncentives, Azure DevOps, Teams.
  • ai: asistente para agentes.
  • privacy: ARCO, retención, datos sensibles.
  • audit: bitácora encadenada.
  • admin y config-admin: usuarios, organizaciones, configuración, tokens, ver como cliente.
  • jobs y queue: procesos en segundo plano.
  • health, settings, openapi, common.

Sesiones y autenticación

MecanismoDetalle
Cookie__Host-sid de 256 bits, Secure, HttpOnly, SameSite=Lax, una por host. Redis guarda solo el SHA-256.
Expiración30 min de inactividad, 12 h absoluta; el identificador rota al completar MFA y al cambiar la contraseña.
CSRFOrigin/Referer exacto + Sec-Fetch-Site, y token X-CSRF-Token por sesión.
ContraseñasArgon2id (19 MiB, t=2), mínimo 12 caracteres, verificación de filtraciones (HIBP, k-anonymity).
MFAObligatorio para ADMIN y AGENT. TOTP con anti-replay y semilla cifrada; WebAuthn/passkeys; códigos de recuperación.
SSO OIDCCode + PKCE; solo identidades vinculadas por el propio usuario; Entra ID para agentes.
ReautenticaciónAcciones sensibles piden contraseña de nuevo (@RequireReauth).
Tokens de APIPersonales, solo personal y host de agentes; se guarda el hash; vigencia ≤ 365 días.

Autorización

Denegar por defecto: cada ruta declara @Public() o @RequirePermissions(). Los permisos salen del rol (ADMIN, AGENT, CUSTOMER) más roles personalizados. El alcance por objeto lo da el acceso a grupos del agente o la organización del cliente; lo que queda fuera de alcance responde 404.

Otros mecanismos

  • Límites de frecuencia en Redis: por ejemplo 5 intentos de login por cuenta cada 15 min, 30 por IP, y límites de subida, descarga y IA.
  • Bitácora: cada registro guarda el hash del anterior (SHA-256); un trigger de la base impide modificar o borrar, y el rol de la aplicación no tiene esos permisos.
  • Tiempo real: Socket.IO autenticado con la misma cookie; los eventos son mínimos ({type, ticketId}) y viajan por el canal Redis mesa:events.
  • Búsqueda: texto completo de PostgreSQL (columna generada con índice GIN, español, inglés y sin acentos).
  • Reglas como datos: condiciones JSON validadas contra un catálogo cerrado (máx. 60 nodos, 4 niveles); control de bucles en triggers.
  • Adjuntos: lista blanca de tipos con verificación de bytes reales, 25 MB, escaneo con ClamAV antes de permitir descarga, URL firmada de 60 s, vistas previas recodificadas sin EXIF.
  • Datos sensibles: detector de RFC, CURP, NSS, CLABE, tarjetas y sueldos en texto y archivos; aviso al cliente y redacción por el agente.

Roles de base de datos

  • app_migrator: dueño del esquema; solo lo usa el contenedor migrator.
  • app_rw: la aplicación; solo SELECT, INSERT, UPDATE y DELETE, máximo 40 conexiones.
  • Conexiones solo por TLS (hostssl) con scram-sha-256.

Migraciones

Prisma Migrate, aplicadas por el desplegador antes de levantar la nueva versión. Política expand/contract: una reversión de imágenes no deshace el esquema, así que cada migración debe ser compatible con la versión anterior (ADR-0008).

Redis

Sesiones (solo hashes), límites de frecuencia, valores de un solo uso (TOTP, OIDC, WebAuthn, CTI), colas BullMQ, pub/sub de eventos y presencia. Persistencia AOF cada segundo.

Arranque de la VM (cloud-init)

Instala Docker y Compose, age, jq, auditd, actualizaciones automáticas, OCI CLI y cosign verificado; endurece sshd, sysctl y Docker; prepara el tmpfs de secretos y el volumen de datos; y deja en /opt/mesa el compose, los scripts y las unidades systemd. Los cambios de cloud-init requieren reemplazar la instancia (terraform plan -replace=oci_core_instance.app), porque metadata está en ignore_changes.

Capacidad de A1

Si OCI responde «Out of host capacity» al crear la instancia, se reintenta el apply en un ciclo hasta que haya capacidad.

09Respaldos y recuperación

Objetivos: RPO ≤ 5 min (≤ 24 h con el volcado inmutable) y RTO ≤ 4 h.

EscenarioProcedimiento
A. Error humanoPITR con restore.sh --time "<fecha>"; los datos actuales se mueven a /srv/mesa/pgdata.before-restore-<fecha>, nunca se borran.
B. Pérdida del servidorterraform apply, secretos, desplegador y restore.sh --latest --yes.
C. Servidor comprometidoRestaurar el volcado inmutable desde un equipo limpio con restore-dump.sh a una base nueva.
D. Prueba trimestralObligatoria; también se prueba en CI en cada cambio.
Llave de age

El servidor solo tiene la llave pública (/opt/mesa/backup-age-recipient.txt). La privada vive en el gestor de contraseñas y en un sobre sellado; sin ella el volcado inmutable no se puede abrir.

Detalle completo: docs/runbooks/restauracion.md y ADR-0009.

10Seguridad

Controles transversales y decisiones de arquitectura.

Secretos

  1. infra/scripts/bootstrap-secrets.sh genera los valores aleatorios, pide los externos y los guarda en OCI Vault; produce secrets.map (nombres y OCID, sin valores).
  2. secrets.map se instala en /opt/mesa/secrets.map.
  3. mesa-secrets-sync lee Vault con el instance principal y escribe archivos 0400 en el tmpfs /run/mesa/secrets.
  4. Un secreto con valor unused deja su integración desactivada. Rotación: docs/runbooks/rotacion-secretos.md.

Cifrado

  • En reposo: llave HSM para volúmenes y buckets; pgBackRest cifrado; age en volcados; AES-256-GCM por campo para semillas TOTP, URLs de Teams y similares (con rotación por id de llave).
  • En tránsito: Cloudflare y túnel; PostgreSQL con TLS dentro de Docker; SMTP con STARTTLS. El cifrado en tránsito del volumen no está disponible en A1.

Navegador

CSP estricta (script-src 'self', sin estilos ni scripts en línea, frame-ancestors 'none'), HSTS de 2 años, nosniff, Permissions-Policy restrictiva, COOP y CORP same-origin.

Gobierno

  • Modelo de amenazas STRIDE con 55 amenazas, mitigación y prueba: docs/seguridad/modelo-amenazas.md.
  • OWASP ASVS 4.0 nivel 2: docs/seguridad/matriz-asvs.md.
  • Respuesta a incidentes (triage ≤ 1 h, LFPDPPP): docs/seguridad/respuesta-incidentes.md.
  • Riesgos aceptados: un solo servidor sin alta disponibilidad, certificado autofirmado de PostgreSQL interno, llave de larga duración de pgBackRest, detectores por patrones (datos sensibles e IA), img-src https: en la CSP.

12Estado de producción

Lo que difiere de la guía de despliegue y lo que queda pendiente, al 20 de octubre de 2026.

Diferencias con la guía de despliegue

  • Hosts en neitek.net con DNS en DigitalOcean y Cloudflare for SaaS (dominio técnico neiteksupport.com), en lugar de una zona propia en Cloudflare.
  • Acceso de operadores por port forwarding de Bastion con llaves en admin_ssh_public_keys; la security list lleva la salida TCP 22 hacia la subred.
  • El aprovisionamiento se hizo desde Windows (OCI CLI en un venv, Git Bash para bootstrap-secrets.sh).

Pendientes

  • Actualizar docs/despliegue.md con las diferencias anteriores.
  • Configurar el correo de Microsoft 365 (envío del sistema y buzones de entrada). Mientras tanto, las invitaciones se generan con un token manual desde el servidor.
  • Completar en Cloudflare el WAF, el límite de autenticación y Cloudflare Access para el host de agentes.
